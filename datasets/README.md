# HumanTrace Dataset

## Overview

HumanTrace is an explainable AI-text detection system designed to analyze college-admissions-style essays.

The dataset is designed to evaluate whether linguistic, stylistic, syntactic, lexical, semantic, and statistical features can distinguish between human-written and machine-generated text.

The dataset is intentionally designed around a realistic scenario:

> A document may be entirely human-written, entirely machine-generated, or partially modified with the assistance of an AI system.

HumanTrace therefore does not treat AI detection as a simple binary classification problem.

---

## Dataset Labels

HumanTrace uses four primary labels:

| Label           | Description                                                       |
| --------------- | ----------------------------------------------------------------- |
| `human`         | Entirely human-written text                                       |
| `ai`            | Entirely machine-generated text                                   |
| `ai_polished`   | Human-written text subsequently modified/polished by an AI system |
| `human_revised` | Human-written text revised by a human                             |

### Why `ai_polished` matters

A realistic admissions essay may begin as human-written and later have selected sentences rewritten or polished using an AI system.

A detector trained only on:

```text
human vs. completely AI-generated
```

may perform well in a controlled experiment while failing on partially AI-assisted writing.

HumanTrace therefore treats mixed-authorship text as an important evaluation category.

## Dataset Record Format

The canonical HumanTrace dataset format is JSONL.

Each line represents one essay.

Example:

```json
{
  "essay_id": "human_000001",
  "text": "Essay text...",
  "label": "human",
  "source": "public_dataset",
  "topic": "education",
  "language": "en",
  "word_count": 487,
  "generation_model": null,
  "generation_temperature": null,
  "generation_prompt_id": null,
  "parent_essay_id": null
}
```

AI-generated example:

```json
{
  "essay_id": "ai_000001",
  "text": "Essay text...",
  "label": "ai",
  "source": "controlled_generation",
  "topic": "education",
  "language": "en",
  "word_count": 492,
  "generation_model": "model-name",
  "generation_temperature": 0.7,
  "generation_prompt_id": "education_001",
  "parent_essay_id": null

```

AI-polished example:

```json
{
  "essay_id": "polished_000001",
  "text": "Modified essay text...",
  "label": "ai_polished",
  "source": "controlled_transformation",
  "topic": "education",

  "generation_model": "model-name",
```

# Data Sources

HumanTrace uses multiple sources rather than relying on a single dataset.

## 1. ASAP Automated Essay Scoring Dataset

The ASAP dataset contains student-written essays from eight essay sets. The essays were written by students in Grades 7–10 and vary substantially in length and characteristics.

Official Kaggle source:

https://www.kaggle.com/c/asap-aes/data

The dataset is useful as a source of human-written educational essays and as an independent evaluation source.

HumanTrace will not assume that every essay in the dataset is automatically appropriate for every experiment. Source, licensing, prompt, length, and topic metadata should be recorded before inclusion.

---

## 2. HC3 — Human ChatGPT Comparison Corpus

HC3 is a human-versus-ChatGPT comparison corpus released for research on machine-generated text detection.

Dataset:

https://huggingface.co/datasets/Hello-SimpleAI/HC3

HC3 contains human and ChatGPT responses and is available under CC BY-SA 4.0, subject to the dataset's source-data licensing notes.

HumanTrace can use HC3 primarily for:

* baseline experiments
* feature analysis
* external evaluation
* comparison with existing AI-text detection research

HC3 should not be treated as the only training source because its distribution is strongly tied to its question-answer setting.

---

## 3. RAID — Robust Evaluation of AI-Generated Text Detectors

RAID is a large benchmark specifically designed for evaluating machine-generated text detectors.

Dataset:

https://huggingface.co/datasets/liamdugan/raid

RAID contains text generated by multiple model families and includes multiple genres, decoding strategies, and adversarial attacks.

The dataset provides metadata including:

* source IDs
* model
* decoding strategy
* repetition penalty
* adversarial attack
* genre/domain

This makes RAID particularly useful as an **external robustness/evaluation dataset**.

HumanTrace should avoid using the complete RAID dataset blindly for training. A cleaner experimental design is to reserve portions or entire generator/domain combinations for out-of-distribution evaluation.

# AI-Generated Data

HumanTrace will generate a controlled AI dataset rather than relying exclusively on an existing AI corpus.

AI samples should be generated from multiple model families where practical.

Each generated sample must record:

* model
* generation prompt
* topic
* generation parameters
* date
* target length
* source essay, if applicable

This metadata is essential for reproducibility.

---

# AI-Polished Data

AI-polished samples are created from human-written source essays.

Example:

```text
Original human essay
        │
        ▼
Selected paragraphs/sentences
        │
        ▼
AI-assisted rewriting
        │
        ▼
AI-polished essay
```

The original essay must remain associated with the transformed version using:

```text
parent_essay_id
```

This allows HumanTrace to evaluate whether the detector can identify partial AI assistance.

---

# Human-Revised Data

Human-revised examples act as a control group.

The goal is to distinguish:

```text
normal human editing
```

from:

```text
AI-assisted editing
```

This prevents the detector from simply treating every polished or grammatically improved essay as AI-generated.

---

# Privacy

HumanTrace's deployed application will not use user-submitted essays as training data.

Production user submissions should be processed transiently.

The application architecture is designed around:

```text
User
  │
  ▼
Flask API
  │
  ▼
In-memory processing
  │
  ▼
Feature extraction
  │
  ▼
Detection
  │
  ▼
Explanation
  │
  ▼
Result
```

Production application data should not be written to:

* a database
* persistent uploaded-file storage
* application logs
* analytics systems

User-submitted text must not silently become part of the research dataset.

Research datasets and production user submissions are separate systems.

---

# Data Validation

Every dataset record must pass validation before entering the processing pipeline.

Required fields:

```text
essay_id
text
label
source
```

Valid labels:

```text
human
ai
ai_polished
human_revised
```

Additional validation should check:

* empty text
* duplicate IDs
* duplicate essays
* invalid labels
* unsupported languages
* extremely short texts
* malformed JSON
* missing metadata
* unexpected encoding
* source/license metadata

---

# Data Leakage Prevention

Dataset splitting must prevent related essays from appearing in different splits.

For example:

```text
human_0001
     │
     └── ai_polished_0001
```

must remain within the same train/validation/test partition.

Otherwise, the detector may effectively see the original essay during training and its modified version during testing.

HumanTrace will therefore use grouped splitting based on:

```text
parent_essay_id
```

where applicable.

# Dataset Development Phases

## Phase 1 — Pilot Dataset

Create a small controlled dataset:

```text
20 human
20 AI
10 AI-polished
10 human-revised
```

Total:

```text
60 samples
```

The purpose of the pilot is to validate the complete data pipeline.

---

## Phase 2 — Feature Dataset

Run every validated essay through:

```text
Preprocessing
      ↓
Feature Engine
      ↓
Feature Vector
```

The resulting feature matrix will be used to investigate which linguistic signals are actually useful.

---

## Phase 3 — Training Dataset

Expand the dataset across:

* topics
* essay lengths
* writing styles
* generation models
* generation settings
* human writing levels

---

## Phase 4 — Robustness Dataset

Evaluate against:

* unseen topics
* unseen models
* different generation settings
* paraphrased text
* AI-polished text
* human-revised text
* adversarially modified text

RAID will be particularly useful for this stage.

---

# Evaluation

HumanTrace will report more than accuracy.

Primary metrics:

* Accuracy
* Precision
* Recall
* F1-score
* ROC-AUC
* False Positive Rate
* False Negative Rate
* Calibration

The project will also document at least three confident failures.

For each failure:

```text
Expected result
Predicted result
Confidence
Relevant features
Possible reason for failure
```

---

# Known Limitations

AI-text detection is not a perfect authorship-verification problem.

A detector may fail when:

* text is heavily edited
* AI output is paraphrased
* the generating model is unseen
* the writing style differs from training data
* the text is very short
* the writer uses highly formulaic language
* the writer is a non-native English speaker

HumanTrace will explicitly evaluate these failure cases rather than hiding them.

The system should therefore present evidence and uncertainty rather than claiming definitive proof of AI authorship.

---

# Reproducibility

Every experiment should record:

* dataset version
* feature version
* preprocessing version
* model version
* random seed
* train/validation/test split
* hyperparameters
* evaluation metrics

This allows experiments to be reproduced after changes to the system.

# Dataset Versioning

Dataset versions will follow:

```text
v0.1 — pilot dataset
v0.2 — expanded dataset
v0.3 — feature-ready dataset
v1.0 — production research dataset
```

Changes to labels, sources, preprocessing, or inclusion criteria should result in a new dataset version.

---

# Goal

The goal of the HumanTrace dataset is not to maximize a single accuracy number.

The goal is to build a detector that:

1. generalizes beyond one AI model,
2. works across multiple writing domains,
3. identifies suspicious passages rather than only producing a document-level score,
4. provides measurable evidence for its predictions,
5. exposes its own failure modes,
6. minimizes false accusations,
7. and does not use production user submissions as training data.
